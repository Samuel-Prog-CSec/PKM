En **TE.CL** se invierten los papeles de [[07 - CL.TE|CL.TE]]: el <mark style="background: #ADCCFFA6;">**front-end** usa `Transfer-Encoding` y el **back-end** usa `Content-Length`</mark>. Se explota distinto, y su caso de uso estrella es el **bypass de WAF**: colar una petición prohibida **dentro** de un chunk que el WAF interpreta como cuerpo inofensivo.

# Preparar Burp

Para manipular el `CL` a mano hacen falta dos ajustes en Repeater:
- **Desactivar `Update Content-Length`** (icono de ajustes junto a *Send*) — si no, Burp recalcula el CL y rompe el ataque.
- Crear un **tab group** con las dos peticiones y enviarlas con <mark style="background: #FFB8EBA6;">*Send group in sequence (single connection)*</mark> — así viajan por el **mismo** socket TCP, condición imprescindible del smuggling.

# El mecanismo

```http
POST / HTTP/1.1
Host: tecl.htb
Content-Length: 3
Transfer-Encoding: chunked

5
HELLO
0

```

- **Proxy (usa TE)**: primer chunk de `5` bytes = `HELLO`, luego chunk `0` = fin. Consume todo.
- **Servidor (usa CL:3)**: el cuerpo son 3 bytes = `5\r\n`. <mark style="background: #FFB8EBA6;">El resto `HELLO\r\n0\r\n\r\n` queda huérfano</mark> → principio de la siguiente petición.

Desync creada. La siguiente petición se contamina con `HELLO...` y el servidor responde con error (método inválido).

# Explotación: bypass de WAF

El WAF bloquea cualquier URL que contenga `admin`. Se cuela `GET /admin` **dentro de un chunk**:

```http
GET /404 HTTP/1.1
Host: tecl.htb
Content-Length: 4
Transfer-Encoding: chunked

25
GET /admin HTTP/1.1
Host: tecl.htb

0

```
(seguida de un `GET /404` normal, ambas por una sola conexión.)

- **WAF (usa TE)**: el primer chunk es `0x25` = **37 bytes** = `GET /admin HTTP/1.1\r\nHost: tecl.htb\r\n` (la petición smuggled hasta el fin de sus cabeceras); la línea en blanco siguiente es el **CRLF de cierre del chunk** (RFC 9112 §7.1), y luego el chunk `0` termina. <mark style="background: #FFB86CA6;">El WAF ve dos `GET /404` — **ninguno contiene `admin` en la URL**</mark> (el `/admin` está "dentro del cuerpo") → los deja pasar.
- **Servidor (usa CL:4)**: el cuerpo de la primera son 4 bytes = `25\r\n`. El resto lo parsea como peticiones nuevas: `GET /404`, `GET /admin` (→ ¡panel admin!), y una tercera inválida.

El log del servidor lo confirma:
```text
[DEBUG] GET /404
[DEBUG] GET /admin
[DEBUG] Invalid request ... Invalid HTTP request line: ''
```

La respuesta a la segunda petición es un `200` con el panel admin → <mark style="background: #8000E1A6;">WAF bypasseado</mark>.

> [!important] Por qué el smuggling es el bypass de WAF definitivo
> El WAF inspecciona lo que **cree** que es la petición; el servidor procesa **otra cosa**. Cualquier filtro basado en la URL, cabeceras o cuerpo se evade escondiendo el payload prohibido en la parte que el WAF interpreta como dato inocuo. <mark style="background: #FFB86CA6;">Sirve para saltarse **cualquier** control del front-end</mark>: no solo `admin`, también reglas anti-SQLi/XSS, listas de IP, o autenticación en el borde. Es de los motivos por los que el smuggling puntúa tan alto.

> [!warning] Cuenta bien los bytes del chunk
> El tamaño del chunk (`0x25` = 37) debe ser **exactamente** la petición smuggled hasta el final de sus cabeceras (`GET /admin HTTP/1.1\r\nHost: tecl.htb\r\n`); la línea en blanco que sigue cierra el chunk. Un byte de más o de menos rompe el parseo. Con *Update Content-Length* desactivado, el `CL` también lo pones tú: aquí `4` = `25\r\n`. Estos ataques son quirúrgicos a nivel de byte — usa la vista Hex de Burp para no equivocarte.
