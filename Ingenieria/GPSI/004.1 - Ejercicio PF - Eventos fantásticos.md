> [!info]+ Enunciado (resumen)
> La empresa **"Eventos fantásticos"** desarrolla una nueva aplicación que integre todo su flujo de trabajo. Requisitos:
> - Mantener información del **evento**: nombre, localización, aforo máximo, horario de apertura y de cierre, fecha de inicio y de fin, y dos listas: una de **asistentes** y otra de **trabajadores**.
> - De cada **asistente**: nombre, teléfono y tipo de pase.
> - De cada **trabajador**: nombre, DNI, salario bruto y su **ficha de especialización**, que se obtiene de la **empresa de contratación** (solo interesa la **especialización principal**).
> - Se puede dar de **alta y de baja** a trabajadores y asistentes; los eventos **solo se dan de alta**; se puede **actualizar** cualquier registro.
> - Mostrar el **número de asistentes** en absoluto y proporcionalmente al aforo, y **avisar** al sobrepasarlo.
> - Al terminar el evento, **generar un informe** estadístico (asistencia, coste de trabajadores y comparación con eventos pasados).
>
> **Pide: Puntos de Función sin ajustar (PFSA).** Método y tablas en [[004 - Estimación del Software]].

## Paso 1 · Frontera

La aplicación medida es **Eventos fantásticos**. Fuera de la frontera está la **empresa de contratación**, que mantiene la *ficha de especialización* y a la que nuestra app accede solo para leer un dato.

## Paso 2 · Funciones de datos

Siguiendo el criterio de clase (en el caso PCGeek, entidades distintas como `Pedido` y `Detalle_Pedido` se cuentan como **ILF separados**), modelamos cada entidad propia con su ILF, no como subgrupos:

- **ILF Evento** — DET: nombre, localización, aforo, horario apertura, horario cierre, fecha inicio, fecha fin (**7**). 1 RET → **Baja → 7**.
- **ILF Asistente** — DET: nombre, teléfono, tipo de pase (**3**). 1 RET → **Baja → 7**.
- **ILF Trabajador** — DET: nombre, DNI, salario bruto, especialización principal (**4**). 1 RET → **Baja → 7**.
- **ELF Ficha de especialización** — la mantiene la empresa de contratación; solo la **leemos** para traer la especialización → es un **ELF** (EIF). Pocos DET, 1 RET → **Baja → 5**.

| Función de datos | Tipo | DET | RET | Complejidad | PF |
| - | - | - | - | - | - |
| Evento | ILF | 7 | 1 | Baja | **7** |
| Asistente | ILF | 3 | 1 | Baja | **7** |
| Trabajador | ILF | 4 | 1 | Baja | **7** |
| Ficha de especialización | ELF | 1-2 | 1 | Baja | **5** |

## Paso 3 · Funciones transaccionales

Alta, baja y modificación son **procesos elementales distintos** → cada uno una **EI** (los eventos solo tienen alta y modificación). Cada EI mantiene su ILF (1 FTR), salvo el **alta de trabajador**, que además **lee la ficha** → 2 FTR → **Media**. Los dos informes **derivan** datos (cuentas, proporciones, totales, comparaciones) → **EO**; al referenciar varios ficheros suben a **Media**.

| # | Transacción | Tipo | DET | FTR | Compl. | PF |
| - | - | - | - | - | - | - |
| 1 | Alta evento | EI | 7 + botón + msg = 9 | 1 | Baja | 3 |
| 2 | Modificar evento | EI | 9 | 1 | Baja | 3 |
| 3 | Alta asistente | EI | 3 + botón + msg = 5 | 1 | Baja | 3 |
| 4 | Baja asistente | EI | id + botón + msg = 3 | 1 | Baja | 3 |
| 5 | Modificar asistente | EI | 5 | 1 | Baja | 3 |
| 6 | **Alta trabajador** | EI | 4 + botón + msg = 6 | **2** (Trabajador + Ficha) | **Media** | **4** |
| 7 | Baja trabajador | EI | 3 | 1 | Baja | 3 |
| 8 | Modificar trabajador | EI | 6 | 1 | Baja | 3 |
| 9 | Nº de asistentes (absoluto + proporción + aviso) | **EO** | ≈ 4 | **2** (Asistente + Evento) | **Media** | **5** |
| 10 | Informe final del evento | **EO** | 6-19 | **3** (Evento + Asistente + Trabajador) | **Media** | **5** |

No hay ninguna consulta de recuperación pura → **0 EQ**.

## Paso 4 · Total

| Tipo | Baja | Media | Alta | PF |
| - | - | - | - | - |
| ILF | 3×7 | | | 21 |
| ELF | 1×5 | | | 5 |
| EI | 7×3 | 1×4 | | 25 |
| EO | | 2×5 | | 10 |
| EQ | | | | 0 |
| | | | **PFSA** | **61** |

> [!success]+ Resultado
> <mark style="background: #8000E1A6;">**PFSA = 61 Puntos de Función sin ajustar.**</mark> (Si pidieran ajustados, se multiplicaría por `0,65 + 0,01 × Total GI`.)

> [!note]+ Decisiones de criterio
> - **Entidades como ILF separados** (Evento, Asistente, Trabajador), siguiendo el criterio de clase para entidades distintas. Si se modelara todo como **un ILF "Evento" con asistentes y trabajadores como RET**, saldrían ≈ **45 PFSA** (un solo ILF y menos FTR en los informes). <mark style="background: #FFB8EBA6;">El propio enunciado de clase avisa: "el resultado final está sujeto a variaciones según la interpretación".</mark> Lo evaluable es **justificar** la elección y aplicar bien el método.
> - **Ficha de especialización = ELF** (la mantiene otra app y solo la leemos). Contrasta con datos que mantiene otra app y que **no** referenciamos (esos no se cuentan).
> - Los informes son **EO** (no EQ) porque calculan: proporción, aviso por umbral, totales y comparación con eventos pasados.
