En **TE.TE**, <mark style="background: #ADCCFFA6;">**ambos** sistemas soportan chunked</mark>, así que no hay discrepancia directa. La grieta: uno de los dos no sigue la especificación al pie de la letra, y **ofuscando** la cabecera `Transfer-Encoding` conseguimos que uno la **acepte** y el otro la **ignore** (cayendo a `Content-Length`). Es la nota de **evasión** del smuggling — la técnica que hace explotable lo que parecía parcheado.

# Ofuscar el `Transfer-Encoding`

El objetivo: desviarse mínimamente del estándar para ver si las dos implementaciones lo parsean **distinto**. Muchos parsers son laxos (buscan solo la subcadena `chunked`) y otros estrictos (exigen coincidencia exacta). Las ofuscaciones clásicas (lista de PortSwigger):

| Técnica | Cabecera |
| - | - |
| Substring match | `Transfer-Encoding: testchunked` |
| Espacio en el nombre | `Transfer-Encoding : chunked` |
| Tab horizontal | `Transfer-Encoding:[\x09]chunked` |
| Tab vertical | `Transfer-Encoding:[\x0b]chunked` |
| Espacio inicial | ` Transfer-Encoding: chunked` |
| Nombre duplicado | dos cabeceras `Transfer-Encoding`, una válida y otra basura |
| Salto de línea en el valor | `Transfer-Encoding:\n chunked` |

(`[\x09]` y `[\x0b]` son los **caracteres** tab horizontal `0x09` y vertical `0x0b`, no el texto literal.)

<mark style="background: #FFB86CA6;">Según **cuál** de los dos sistemas se trague la ofuscación, el escenario se reduce a [[07 - CL.TE|CL.TE]] (si el proxy ignora el TE) o a [[09 - TE.CL|TE.CL]] (si lo ignora el servidor)</mark>.

# Identificación

Sobre un lab que **no** es CL.TE simple pero sí TE.TE: se toma el request de siempre y se sustituye el **espacio** que separa `Transfer-Encoding:` de `chunked` por un **tab horizontal**. En Burp Repeater se hace desde la vista **Hex**, cambiando el byte `0x20` (espacio) por `0x09` (tab):

```http
POST / HTTP/1.1
Host: tete.htb
Content-Length: 10
Transfer-Encoding:<TAB>chunked

0

HELLO
```

Enviándolo dos veces seguidas, el segundo response da **405**: el proxy ignoró el `TE` ofuscado (cayó a CL) mientras el servidor sí lo procesó → efectivamente un CL.TE.

# Explotación

Idéntica a [[07 - CL.TE|CL.TE]], solo que **ofuscando el TE** para forzar al proxy a caer a CL. Para que el admin revele la flag:

```http
POST / HTTP/1.1
Host: tete.htb
Content-Length: 47
Transfer-Encoding:<TAB>chunked

0

GET /admin?reveal_flag=1 HTTP/1.1
Dummy: 
```

> [!warning] Fiabilidad: el smuggling es sensible al timing
> Los ataques a otros usuarios son **time-sensitive**: la petición de la víctima tiene que llegar al servidor **justo después** de la tuya, por el mismo socket. Y hay más de un socket: <mark style="background: #FFB8EBA6;">múltiples **worker threads** y **connection pools**</mark> hacen que tu prefijo huérfano y la víctima puedan caer en conexiones distintas. En la práctica hay que **repetir** el envío (≈1/seg) hasta acertar la ventana. No es "un disparo y listo": es probabilístico.

> [!success] Automatización
> Probar todas estas ofuscaciones a mano es tedioso. La extensión **HTTP Request Smuggler** de Burp prueba <mark style="background: #FF5582A6;">toda la matriz de ofuscaciones TE/CL automáticamente</mark> y confirma la desync por timing de forma segura. Es la herramienta estándar; el detalle en [[12 - Herramientas y prevención de Request Smuggling]].

La siguiente variante, [[09 - TE.CL|TE.CL]], invierte los papeles: el front-end usa `Transfer-Encoding` y el back-end `Content-Length`.
